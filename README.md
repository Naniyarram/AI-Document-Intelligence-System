## 📖 The Engineering Story

When enterprises process invoices, contracts, and financial reports, traditional OCR and simple keyword search pipelines break down. They fail on nested tables, visual noise, and complex semantic queries. 

I built this platform to solve that using a modern AI engineering stack. Instead of a simple wrapper around an LLM API, this project implements a **6-stage retrieval-augmented generation (RAG) pipeline** focused on robustness, cost-efficiency, and accuracy. 

### Key Architectural Decisions:
1. **Multimodal Ingestion (VLM):** Instead of fragile OCR heuristics, I integrated **Qwen2.5-VL-7B** to process scanned pages, charts, and embedded images natively.
2. **Table-Aware Chunking:** Standard chunking destroys tabular structures. I implemented a heuristic router that detects tables (via pipe/tab density) and bypasses the `RecursiveCharacterTextSplitter`, preserving rows and columns for the LLM.
3. **Hybrid Retrieval with Cross-Encoder:** Semantic search (Cosine Similarity) fails at exact keyword matching (like invoice IDs). I implemented a hybrid retrieval strategy: merging top candidates from **BM25 (lexical)** and **ChromaDB (semantic)**, deduplicating them, and scoring them through an **ms-marco Cross-Encoder** for the final context window.
4. **LLM-as-a-Judge Faithfulness:** To combat hallucinations, answers are processed asynchronously by a secondary prompt that verifies every claim against the retrieved chunks, returning a `Supported / Not Supported` confidence score.
5. **Decoupled Embeddings:** To ensure the system runs smoothly across environments (and to bypass a known ONNX runtime DLL issue on Windows), I decoupled the embedding generation from ChromaDB, manually passing vectors generated by `sentence-transformers` into the persistent local store.

## 🏗️ System Architecture

The pipeline is decoupled into discrete stages, ensuring the backend (FastAPI) and frontend (Streamlit) scale independently.

```mermaid
flowchart LR
    A["Business Documents"] --> B["Ingestion Layer<br/>PDF / DOCX / XLSX / CSV / Images / PPTX"]
    B --> C["Visual Understanding<br/>VLM (Qwen2.5) for scans, charts, tables"]
    C --> D["Semantic Chunking<br/>LangChain Recursive Splitter (Table-Aware)"]
    D --> E["Embedding + Indexing<br/>Sentence Transformers + ChromaDB"]
    E --> F["Hybrid Retrieval<br/>BM25 + Dense Search + Cross-Encoder"]
    F --> G["Grounded Generation<br/>Llama-3.3-70B with source-aware prompting"]
    G --> H["Outputs<br/>Q&A, extraction, anomaly review, confidence signals"]
```

## 💻 Tech Stack

* **Backend:** Python, FastAPI, Docker
* **Frontend:** Streamlit
* **AI/LLM Serving:** OpenRouter API (Llama-3.3-70B, Qwen2.5-VL-7B)
* **Embeddings & Reranking:** `all-MiniLM-L6-v2`, `cross-encoder/ms-marco-MiniLM-L-6-v2` (Local execution to save API costs)
* **Retrieval & Storage:** ChromaDB (Vector DB), BM25 (`rank-bm25`)
* **Document Parsing:** PyMuPDF, python-docx, openpyxl, python-pptx
* **MLOps & Quality:** pytest, LLM-as-a-judge faithfulness scoring

## 🛠️ Local Installation & Setup

1. **Clone and Setup Virtual Environment:**
```bash
git clone https://github.com/Naniyarram/ai-document-intelligence-system.git
cd ai-document-intelligence-system
python -m venv .venv
source .venv/bin/activate  # On Windows: .venv\Scripts\activate
pip install -r requirements.txt
python -m spacy download en_core_web_sm
```

2. **Environment Configuration:**
```bash
cp .env.example .env
```
*Add your OpenRouter API key to `.env`.*

3. **Run via Docker (Recommended):**
```bash
docker-compose up --build
```
*The app will be available at `http://localhost:8501`*

## 📈 Scalability & Future Improvements

While this repository is a production-ready proof of concept, a true enterprise deployment would require:
- **Distributed Vector DB:** Migrating from the local SQLite-backed ChromaDB `PersistentClient` to a distributed cluster like Milvus or Qdrant for horizontal scaling.
- **Asynchronous Workers:** Moving the heavy ingestion and VLM processing steps into a Celery/Redis background queue so they do not block the FastAPI worker threads during large document uploads.
- **Score Normalization:** Currently, BM25 and Dense scores are merged via max-score division. Implementing Reciprocal Rank Fusion (RRF) would provide a mathematically sounder merging strategy.
